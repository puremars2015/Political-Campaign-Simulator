# 《選戰辦公室：距離投票還有90天》開發計畫

文件狀態：初版開發基準，可隨原型測試修訂。

建立日期：2026-10-28（Asia/Taipei）。

產品類型：單人、文字敘事、回合決策、政治模擬網頁遊戲。

## 1. 產品目標

玩家隨機成為一名候選人的競選辦公室主任，在時間、預算、候選人立場、團隊壓力、民調與選票之間做選擇。玩家負責推進選戰，但無法完全控制候選人、組織與事件。

核心體驗是：**「我一開始明明不打算做這個承諾，但我記得，是哪幾次看似合理的選擇，讓我們走到了這裡。」**

遊戲應讓玩家理解政見如何在合理但互相衝突的要求中逐漸形成、縮減或反轉。勝選是重要目標，但結局也應呈現團隊、信用與承諾的代價。

### 1.1 設計原則

- 玩家扮演有影響力但受限制的競辦主任，不是全知的候選人操控者。
- 困境來自可理解的因果與資源限制，不能只是所有選項都會受罰。
- 政策選擇有不同價值與成本，不標記標準道德答案。
- 保留談判、延後、縮小承諾、維持原則與承受代價的空間。
- 民調是有誤差、延遲與解讀爭議的資訊，不是每次選擇的即時分數。
- 重要後果能透過事件紀錄追溯，但不必立即揭露隱藏選情。
- 真人公開紀錄、模型推論與遊戲虛構必須可以區分。

### 1.2 參考作品與查證狀態

參考網址：https://1in8b.life/zh/ 。採用使用者提出的「隨機人生、事件選擇、累積後果」作為設計方向。

規劃時該網站回傳 HTTP 403，尚未驗證其實際介面、數值機制或完整流程。後續如能正常存取，再補充玩法分析；現階段不宣稱已重現參考作品，也不複製其素材、文案或視覺設計。

## 2. 背景與版本範圍

正式內容方向以2026年台灣地方選舉為背景，首個職位聚焦縣市長。其他職位的選制、權責與議題差異留待後續版本設計。

原型先使用一個虛構縣市與三名合成候選人，驗證核心玩法；真人資料包在公開資料查證與內容審閱完成後才加入。原型內容不得被描述成真實候選人的經歷或立場。

### 2.1 MVP 必備範圍

| 項目 | 首版目標 |
| --- | --- |
| 遊戲形式 | 單人、手機優先的文字網頁遊戲 |
| 單局長度 | 約30至45分鐘，需由試玩驗證 |
| 選戰時間 | 90天濃縮為12回合，末段採每日倒數敘事 |
| 選區與候選人 | 一個虛構縣市、三名合成候選人 |
| 劇情內容 | 約30個有條件、可重組的事件 |
| 核心系統 | 有限行動、政見承諾、候選人協調、民調、延遲後果 |
| 結局 | 開票、承諾變化、團隊關係、執政負擔回顧 |
| 保存 | 自動存檔、繼續遊戲、結束後以相同種子重玩 |

### 2.2 首版不納入

- 真實候選人全集、全台選區、議員或其他職位選制。
- 多人對戰、帳號系統、雲端同步、付費功能。
- 無限制自由輸入政見或自動生成真人事件。
- 真實選情預測、實際競選成效評估工具。
- 選後完整施政模擬；首版以結局呈現承諾負擔。

## 3. 玩家旅程與核心循環

### 3.1 開局

1. 先說明遊戲中的虛構內容與模擬結果性質。
2. 隨機分配候選人、選情與辦公室起始條件。
3. 閱讀候選人簡介、歷史立場與接手時已存在的承諾。
4. 接到第一份選戰簡報，透過首個事件學習決策。

隨機模式保留「被分配到這段人生」的感受。完成一局後可開放自由選角，供探索與比較。開發模式可直接指定候選人與隨機種子。

### 3.2 每回合流程

**閱讀簡報 → 安排行動 → 處理事件 → 協調公開立場 → 結算與保存。**

- 簡報：新聞、民調、群組訊息、資源與待處理承諾。
- 行動：政策研究、議題回應、行程、團隊照顧、調查或危機處理。
- 事件：提供情境、期限、選項與可理解的代價提示。
- 協調：候選人可能接受、要求修改或拒絕提案。
- 結算：呈現已知結果，排入延遲後果，推進日期並自動存檔。

初始每回合配置三個行動點，行動成本與數值在平衡測試後調整。免費閱讀資料不消耗行動點；高成本行動必須在確認前說明。延後處理也必須有明確規則與紀錄。

### 3.3 12回合節奏

| 回合 | 敘事定位 | 系統重點 |
| --- | --- | --- |
| 1–3 | 接手、盤點與建立關係 | 教學、初始承諾、候選人信任 |
| 4–6 | 政見成形與議題交鋒 | 資源競爭、公開措辭、早期後果 |
| 7–9 | 壓力累積與立場檢驗 | 歷史矛盾、延遲後果、團隊疲勞 |
| 10–12 | 投票前逐日倒數 | 有限修正、承諾鎖定、最後決策 |

每個回合保存明確的日期區間；前三階段合計覆蓋至投票前三天，最後三回合逐日推進。投票與開票在第12回合結束後觸發。

## 4. 模擬系統

### 4.1 玩家可見的主要狀態

| 狀態 | 用途 | 呈現原則 |
| --- | --- | --- |
| 經費 | 支付調查、活動與其他行動 | 顯示餘額與支出紀錄 |
| 時間／行動點 | 限制同回合能處理的事 | 明確顯示剩餘額度 |
| 團隊士氣 | 影響執行能力、疲勞與離職事件 | 數值搭配成員訊息 |
| 候選人信任 | 影響建議是否被接受、談判空間 | 說明關係變化的已知原因 |
| 公共信任 | 累積承諾可信度與言行影響 | 呈現有誤差的內部評估，不當作客觀讀心值 |
| 政策一致性 | 紀錄目前立場與歷史承諾的關係 | 能展開查看具體矛盾與理由 |

關係、承諾、事件旗標與疲勞細節可作為次級狀態，避免首頁變成過度複雜的儀表板。數值上下限、成本與效果集中配置，不分散寫在介面中。

### 4.2 候選人自主性

候選人具有公開履歷、議題立場、性格、優先事項與可協商範圍。玩家提出方案後，系統依既有立場、當前信任、事件壓力與歷史選擇決定回應。

- 接受：按提案執行。
- 協商：提出可接受的修訂，玩家仍能選擇。
- 拒絕：說明理由與目前可用的替代方案。
- 自行決定：僅在事件預先定義且條件成立時發生，必須留下因果紀錄。

信任提供談判空間，但不應讓所有原則都能靠刷好感度取消。重要限制應提前透過簡報、對話或公開紀錄提示。

### 4.3 政見承諾系統

每項政見至少包含：問題、目標、政策工具、規模、財源、期限、公開措辭與目前狀態。

公開措辭區分「研議」「推動」「承諾完成」等強度。修改強度、規模或期限會同步改變成本、可行性、辨識度與履約風險。

狀態流程：草案 → 內部協調 → 公開承諾 → 修訂／撤回／維持至結局。

所有變更保留前後版本、回合、觸發事件與玩家選擇。撤回不能直接刪除歷史；合理修訂也不應自動被視為不誠實。財源、權責與期限需由規則檢查，無法執行的承諾可以被提出，但必須留下警示與後續負擔。

### 4.4 民調與隱藏選情

分開保存三種資料：

1. 模擬中的實際選情：候選人支持、未表態與投票傾向等隱藏狀態。
2. 民調觀測：調查時間、樣本數、調查方式、支持率、未表態與不確定性。
3. 幕僚解讀：從可見資訊形成的判讀，可能不完整。

行動效果不直接等於得票效果；聲量、信任與支持需分開處理。政策影響可有延遲，調查不一定反映當下最新變化。

首版先採固定抽樣模型，定義清楚支持率分母、未表態處理與誤差呈現方式。調查方法的誤差說明必須與實際模型相符；不把抽樣誤差當作涵蓋所有不確定性的保證。

買更多調查可減少部分資訊盲點，但不能直接讀取隱藏狀態。一般遊戲畫面不揭露引擎真值，開發工具可查看以協助除錯。

### 4.5 事件與延遲後果

事件由前置條件、觸發窗口、選項、即時效果、延遲效果與後續事件組成。主線事件確保節奏，條件事件回應玩家歷史，隨機事件提供變化。

- 不同候選人可共用事件骨架，但對話、可用選項與反應應不同。
- 一次性事件不可重複觸發；互斥事件需有明確群組。
- 關鍵後果必須保存來源決策，供回顧與開發檢查。
- 任何資源狀態下都須存在有效選項，避免流程卡死。
- 經費不足或士氣低落應開啟有代價的替代路徑，不直接令遊戲無法繼續。

事件題材包含居民陳情、政策爭議、冷清活動、幕僚離職、採訪、辯論、失言與內部協調，不以醜聞作為唯一戲劇來源。

### 4.6 代表事件：補助承諾

情境：對手宣布大規模補助，記者要求回應。候選人希望跟進，但政策組提醒候選人上週才批評同類承諾缺乏財源。距離記者會還有20分鐘。

| 選擇 | 當下代價 | 可能延遲後果 |
| --- | --- | --- |
| 維持原立場，說明財源與權責 | 準備時間與曝光機會 | 形成一致性紀錄，也可能遭批缺乏回應 |
| 提出較小且有條件的版本 | 研究與協調成本 | 政見分化，後續須說明資格與財源 |
| 宣布研究中 | 承受拖延批評 | 爭取評估時間，但下一次必須回覆 |
| 跟進並要求事後補方案 | 政策組壓力與信用風險 | 預算缺口、辯論追問、承諾負擔 |

具體結果由候選人與先前事件共同決定。選項提示描述已知成本，不提供固定的「支持度＋3」答案。

## 5. 結局與開票

投票模型根據隱藏支持、未表態分配、投票傾向與有界隨機因素產生結果。模型參數必須配置化，經模擬測試檢查，不宣稱對真實選舉具預測能力。

開票依虛構地區逐步揭曉，票數加總須一致；平票與其他邊界情況須有明確的遊戲規則。開票隨機性不能任意抹去玩家整局累積的影響。

結局包含四份回顧：

- 選票：得票、差距、模型中主要影響因素。除非實際運算反事實比較，不宣稱某次選擇精確造成多少票。
- 承諾：起始與最終政見、修訂與反轉的時間軸。
- 團隊：成員去留、士氣、候選人關係。
- 代價：若當選，尚未解決的財源、可行性與期限；若落選，留下的組織與政策成果。

勝選但失去政策主導權、落選但維持團隊等結果，都應有完整敘事。結局不提供單一的道德總分。

## 6. 介面與可及性

| 畫面 | 主要內容 |
| --- | --- |
| 開局 | 內容說明、隨機分配、候選人與辦公室介紹 |
| 每日簡報 | 日期、民調、資源、新聞、待處理事項 |
| 辦公室群組 | 成員壓力、關係與事件對話 |
| 決策卡 | 情境、期限、可選行動、已知成本與限制理由 |
| 政見資料夾 | 歷史立場、草案、公開承諾與版本差異 |
| 選戰紀錄 | 已發生決策與可知後果，不洩露隱藏狀態 |

採繁體中文、手機優先排版，桌面可並列簡報與事件。文字可調整大小，鍵盤可完成全部決策，狀態不能只靠顏色表達。動畫可略過，關閉頁面不應丟失已提交選擇。

## 7. 技術方案與資料模型

### 7.1 建議技術基線

儲存庫目前尚無應用程式或依賴，以下為待實作方案，並非已完成安裝的技術棧。

- 前端：TypeScript、React、Vite。
- 規則引擎：獨立的純 TypeScript 模組，與畫面分離。
- 內容：版本控制中的結構化 JSON，載入時進行 schema 驗證。
- 存檔：首版採 localStorage，包裝成可替換的儲存介面。
- 測試：Vitest 驗證引擎與資料；Playwright 驗證完整玩家流程。
- 首版不需後端、登入、外部 API 或生成式 AI 服務。

建立專案時固定套件管理器與 lockfile。由實作階段選擇相容的穩定版本，將實際版本與指令寫入開發說明。

建議模組：`engine`（回合與規則）、`content`（事件與候選人）、`storage`（保存與遷移）、`ui`（畫面）、`tests`（驗證）。

### 7.2 核心資料實體

| 實體 | 必要欄位或責任 |
| --- | --- |
| Candidate | ID、背景、立場歷史、性格、協商限制、初始關係 |
| District | ID、議題、虛構地區、基礎選情與模型參數 |
| GameState | schema版本、內容版本、種子、亂數狀態、回合、日期、階段、資源、旗標 |
| PolicyCommitment | ID、議題、工具、規模、財源、期限、措辭、狀態、變更歷史 |
| EventDefinition | ID、條件、窗口、優先序、互斥群組、選項、效果 |
| PendingEffect | 到期回合、效果內容、來源事件與決策ID |
| Poll | 調查時間、方法、樣本、支持率、未表態、誤差資訊 |
| DecisionRecord | 回合、事件、選項、狀態變更、承諾變更、公開敘事 |
| ElectionResult | 各地區票數、總票數、勝負、模型與種子資訊 |
| SourceRecord | 真人資料包使用的來源網址、日期、引文、情境與查證狀態 |

### 7.3 引擎契約與存檔

- 相同初始種子、內容版本與選擇序列，必須得到相同結果。
- 隨機抽樣一律透過可保存狀態的亂數產生器，不直接呼叫散落的隨機函式。
- UI 提交行動，引擎驗證前置條件與成本，再一次性產生新狀態與紀錄。
- 拒絕不合法行動時不扣資源、不推進時間。
- 決策提交與回合結算後自動保存；重複點擊不可重複扣款或套用效果。
- 保存完整狀態與決策紀錄，不依賴重新整理後重新抽取事件。
- 內容或schema版本不相容時明確說明；不得靜默重置舊存檔。
- 儲存失敗時提示使用者並保留當前畫面狀態，不能假裝已保存。

## 8. 真實選舉資料包規範

真人版本另設內容里程碑，不能以虛構原型的完成代表真人版本已完成。

### 8.1 資料蒐集

- 參選與選制資訊優先使用選務機關的正式資料。
- 政見使用候選人正式公開資料；歷史立場交叉參考公開發言、議事紀錄與可靠報導。
- 每筆立場附來源、日期、適用職位與情境，保留修正歷程。
- 標示資料截至日期；未宣布、待確認與已確認分開處理。
- 未取得證據時保留未知，不自行補成候選人的既定主張。

### 8.2 事實、推論與虛構

- 公開紀錄可引用並追溯來源。
- 性格參數與協商邊界是設計推論，需標示並人工審閱。
- 競辦對話與內部事件是虛構，不當作私人動機的事實陳述。
- 不將虛構醜聞、犯罪或利益交換套在真人身上。
- 遊戲內提供查閱來源與辨識內容性質的入口。
- 如未來使用生成式文字，只能在審核過的事實與情境範圍內改寫，不自由生成真人事實。

## 9. 開發階段與交付條件

以下按依賴順序推進，以交付條件估算工作，不預先承諾缺乏人力依據的日程。

### M0：規格與內容骨架

交付：三名合成候選人、一個虛構縣市、初始政見、12回合日期配置、事件schema及三個代表事件。

驗收：各候選人至少有可辨識的限制與協商差異；每個事件具備前置條件、代價與可追溯後果；資料驗證能指出缺漏與無效引用。

### M1：可完整操作的垂直切片

交付：專案基礎、規則引擎、開局、前三回合、一次政見修改、一次候選人協商、一次延遲後果與自動存檔。

驗收：玩家能完成開局至第三回合；重新整理能繼續；相同種子與選擇能重現結果；選項限制有理由；至少一項早期選擇會改變後續事件。

### M2：完整 MVP

交付：約30個事件、完整12回合、民調、投票模型、開票與四份結局回顧。

驗收：三名候選人均可完成一局；正常與低資源路徑均不會卡死；承諾版本可追溯；開票票數一致；支持率與資源不出現不合法數值。

### M3：試玩、平衡與可及性

交付：手機版改善、鍵盤操作、錯誤處理、平衡報告與修訂內容。

至少邀請五名未參與開發者試玩，紀錄實際遊玩時間、誤解與卡關位置。觀察玩家能否解釋一次立場轉變、感受到候選人自主性，並區分民調與實際結果。若玩家只是在尋找固定最高分答案，優先調整回饋與事件因果。

驗收：核心流程無阻斷問題；主要選項有可理解的取捨；不同候選人出現不同選擇空間；沒有一項重複行動在所有情境下都支配其他行動。

### M4：2026真人資料包

交付：選定縣市與候選人名單、來源庫、資料更新流程、人工審閱紀錄、事實／推論／虛構標示。

驗收：納入範圍的候選人狀態、職權與政見均已查證；公開紀錄可追溯；虛構事件不被呈現成真人事實；資料更新不破壞既有存檔。符合後才宣稱支援2026真實選舉內容。

## 10. 測試與驗收策略

| 類型 | 必要驗證 |
| --- | --- |
| 引擎單元測試 | 資源扣除、非法行動、階段轉換、候選人拒絕、承諾版本、延遲效果 |
| 確定性測試 | 固定種子與決策序列可重現；存讀檔前後的後續結果一致 |
| 內容驗證 | ID唯一、引用存在、窗口有效、一次性與互斥事件符合規則 |
| 存檔測試 | 重新整理、損壞資料、版本不相容、儲存失敗與重複提交 |
| 統計與邊界測試 | 支持率合法、票數加總、未表態處理、平票、資源極值 |
| 完整流程測試 | 各候選人從開局到結局，至少包含一條低資源與一條承諾反轉路徑 |
| 介面驗證 | 手機閱讀、鍵盤操作、文字縮放、非色彩提示與動畫略過 |
| 人工內容審查 | 因果可理解、無固定道德答案、來源標示、人物內容邊界 |

自動模擬使用固定種子集合覆蓋多種路徑，以找出卡死、異常數值與單一策略支配問題；模擬結果不替代真人試玩。紀錄執行版本、種子與結果，使問題可以重現。

實作後至少提供安裝、開發啟動、建置、型別檢查、引擎測試與端到端測試指令，並記錄實際通過與未通過項目。本文件本身不代表任何應用程式測試已執行。

## 11. 主要風險與處理

| 風險 | 處理方式 |
| --- | --- |
| 選項看似不同、後果卻一樣 | 在垂直切片先驗證會改變後續事件的決策 |
| 所有決策都懲罰玩家 | 同時設計可獲益的協商與有代價的原則路徑 |
| 候選人自主性讓玩家失去參與感 | 提前提示限制，保留替代方案，建立信任可換取的談判空間 |
| 民調變成即時得分表 | 分離聲量、信任、支持與調查觀測，延遲呈現部分結果 |
| 隨機性蓋過玩家決策 | 限制擾動範圍，檢查固定種子下決策差異與結局分布 |
| 內容組合爆量 | 共用事件骨架，以條件與候選人差異控制分支數量 |
| 真人資料過期或失真 | 保存來源與截至日期，設立更新與審閱門檻 |
| 模擬被誤認為預測 | 開局、民調與結局標示遊戲模型性質 |
| 太早擴充導致首局無法完成 | M2以前不增加選區、職位、後端或生成式服務 |
